# Load-test scripts

k6 scripts for the four user-journey scenarios in the performance
addendum (§2.5). **These have not been run.** This environment has no k6
binary and no staging deployment of JBS to point them at — writing and
running a load test are different deliverables, and only the first one
was possible here. Treat everything below as reviewed-but-unexecuted.

## What's here

| Script | Scenario | Requires |
|---|---|---|
| `scenario_a_browse.js` | Browse job posts + matches (read-only) | A seeded test account with some job posts/matches |
| `scenario_b_upload.js` | Upload a CV, poll through the extraction pipeline | A seeded test account, a CV fixture file |
| `scenario_c_generate.js` | Match -> tailored CV -> export, staged latency | A seeded test account with a parsed CV + parsed job post |
| `scenario_d_burst.js` | Concurrent match-request burst (stress test) | Same as C |

Cover-letter generation (`/cover-letters/start` -> `/answers` ->
`/regenerate`) is not scripted — it's an interactive Q&A flow, not a
fire-and-poll job, and faking the answers would produce latency numbers
that don't reflect real usage. A dedicated script for it is a reasonable
follow-up, not something to approximate here.

## Before running these for real

1. **Install k6**: https://k6.io/docs/get-started/installation/
2. **Never point these at production or the shared dev database.** Use a
   dedicated staging deployment, ideally seeded the way
   `backend/tests/conftest.py` isolates the pytest database — a shared,
   unisolated target will accumulate exactly the kind of stray-row
   pollution that motivated giving pytest its own database.
3. **Seeding**: create test accounts (suggested convention:
   `loadtest+N@test.example`, matching the existing `@test.example`
   convention used by the pytest suite) with at least one parsed CV and
   one parsed job post each, and record the relevant IDs as env vars.
   The representative-data-set sizes in the addendum (§2.4 — 10k users,
   20k CVs, 50k job posts) are a target for a real staging seed script,
   not something generated by these k6 scripts themselves.
4. **Fixtures**: `scenario_b_upload.js` needs `FIXTURE_CV_PATH` pointing
   at a real PDF/DOCX. None is committed here — use any representative,
   non-sensitive CV-shaped document.
5. **Stubbed AI provider for baseline runs**: Scenario C's tailored-CV and
   export stages call through to the real LLM client
   (`app/services/llm_client.py`) unless the target environment stubs it.
   Run against a stub first (deterministic, no real spend) before ever
   pointing this at a real OpenAI-backed environment — `COST_USD_COUNTER`
   in `app/core/metrics.py` is real spend tracking, not a load-test safety
   rail.

## Example invocation

```sh
k6 run -e BASE_URL=https://staging.example \
       -e TEST_EMAIL=loadtest+1@test.example \
       -e TEST_PASSWORD=... \
       scenario_a_browse.js
```

## Target thresholds

See the addendum's §2.2 table for the full list; the thresholds encoded
in each script here are the read/write/upload-ack subset that applies to
that scenario specifically. Report format follows §2.10 — commit SHA,
environment, seed version, p50/p95/p99, error rate, queue depth, and a
bottleneck diagnosis, not just a pass/fail.
