# Diagnosing Quality Failures in LLM-Backed Systems: A Methodological Account

## Abstract

This essay documents the diagnostic method used to isolate why an evidence-bound CV tailoring system produced output measurably worse than its own input. The investigation found four independent structural defects and one quantifiable stylistic regression, none of which were attributable to the language model — the component most people suspect first. The method is generalisable: it applies to any system where a probabilistic component sits inside a deterministic pipeline, and where "the AI isn't very good" is the tempting but usually wrong conclusion. The essay is written for a developer early in their career who has been handed a system that produces bad output and asked to find out why.

---

## 1. The problem class

Systems built around large language models present a distinctive debugging difficulty: they fail *softly*. A null pointer throws. A malformed query errors. But a system that produces a plausible-looking CV with the candidate's education missing produces no exception, no log line, no alert. It returns HTTP 200 and a document. The failure is only visible to a human reading the output and noticing something is absent.

This softness has a second consequence. Because the output is generated by a model, and models are known to be imperfect, the model becomes the default suspect. The reasoning is superficially sound — the model wrote the text, the text is bad, therefore the model is bad — and it is almost always wrong. In the case documented here, the model was the only component in the chain that was working as intended.

The core methodological claim of this essay: **in an LLM-backed pipeline, the model is the last thing you should suspect, not the first.** Everything upstream of it — parsing, filtering, schema definition, prompt construction — is deterministic code that you wrote, and deterministic code is where reproducible bugs live.

---

## 2. Establishing a control

The first move in any diagnosis is to find something to measure against. The reported symptom was subjective: "the CV doesn't look right." Subjective symptoms cannot be debugged. They must first be converted into something countable.

In this case a control was available and obvious in retrospect: the *original* CV. The system's job is to transform an input document into a tailored output document. That gives a natural before/after pair, and any property of the output can be compared against the same property of the input.

The first measurement was trivial:

```
Original CV:   49 non-empty paragraphs
Tailored CV:   13 non-empty paragraphs
```

This single number reframed the entire investigation. A tailoring system should *reorganise and reweight* content. A 73% reduction in paragraph count is not tailoring; it is deletion. Before understanding any mechanism, we now knew the failure mode's shape: the system was removing content, not transforming it.

**Principle: convert the subjective complaint into a number before forming any hypothesis.** "Looks wrong" is unfalsifiable. "Lost 73% of its paragraphs" tells you where to look.

---

## 3. Reading the code, not the documentation

The system under investigation was unusually well documented. Every module had a substantial docstring explaining its design rationale. This turned out to be a hazard.

One function's docstring described its behaviour as checking for *"overlapping date ranges with conflicting titles."* Reading the function body revealed it compared only company name and job title — no date field was read, parsed, or compared anywhere in it. The documentation described an intention; the code implemented something narrower.

This was not a one-off. The same codebase contained a module docstring asserting "no dependencies beyond the standard library" in a file that imported a third-party HTTP client, and a prompt template instructing the model to produce "bullet points" (plural) alongside a schema that could physically hold only one string.

**Principle: documentation records intent at the moment of writing; code records behaviour at the moment of execution. When they disagree, the code is authoritative.** Docstrings drift because they are written before implementation and rarely revisited when the implementation changes. A junior developer's instinct — reasonably — is to trust the documentation as a shortcut to understanding. In diagnosis, that shortcut is the trap.

The practical discipline: when a docstring makes a specific behavioural claim, locate the lines that implement that claim before believing it. If you cannot point at them, the claim is unverified.

---

## 4. Reproducing the failure in isolation

The most visible symptom was that a CV listing 27 professional skills produced a tailored version containing two: `CSS, HTML`.

The relevant code path was short. Skills were filtered to those the matching engine had cited, and the matching rule was:

```python
req_text == cand_text or req_text in cand_text or cand_text in req_text
```

Reading this, a hypothesis formed: the third clause — `cand_text in req_text` — means a skill survives if its name appears *inside* a requirement sentence. That would systematically favour short generic tokens over long specific ones.

A hypothesis is not a finding. The next step was to reproduce it in isolation: extract the rule into a standalone script, feed it the candidate's real 27 skills and six requirement strings phrased the way job advertisements actually phrase them, and observe the result.

```
Requirements tested: 6
Skills matched:  CSS, HTML, accessibility, component libraries,
                 design systems, stakeholder management
Skills dropped:  21
```

The reproduction confirmed the mechanism and explained the specific survivors. "HTML" appears inside the sentence "Ability to work with HTML and CSS." "Figma" appears inside no requirement sentence, because job advertisements say "prototyping tools," not "Figma." The rule was not randomly lossy — it was *systematically biased against specificity*, discarding precisely the skills that distinguish a candidate.

**Principle: a hypothesis derived from reading code becomes a finding only when you execute the code in isolation and observe the predicted behaviour.** Reading suggests; running proves. The isolation matters because it removes every confound — no database, no model, no pipeline, just the rule and its inputs.

---

## 5. Differential diagnosis: locating the failing layer

The second symptom was that education had vanished entirely. The pipeline had four candidate layers where it could have been lost: parsing, matching, generation, or rendering.

Rather than guessing, each layer was eliminated in turn, starting with the one most easily falsified. The generation function was read first:

```python
if not education_items and not certification_items:
    return None
```

Its docstring claimed it used unfiltered rows, and unlike the earlier case, the body confirmed it: no relevance filter, an explicit combined gate, a section returned whenever either list was non-empty. The generator was therefore *correct*, and could only produce nothing if it received nothing. That eliminated generation and rendering in one step and pointed upstream to parsing.

The parser was then tested against the candidate's four actual education lines:

| Line | degree keyword | institution keyword | Outcome |
|---|---|---|---|
| Google's UX Design Certificate — Coursera | no | no | discarded |
| Diploma in Application Development — Karrox | yes | no | parsed |
| How to Build Digital Products — Product School | no | no | discarded |
| User Experience — FutureLearn | no | no | discarded |

Three of four hit a `return None` branch commented `# ambiguous — never guess which side is which`. The parser recognised only traditional academic credentials — `University|College|Institute|Polytechnic|Academy` and conventional degree abbreviations. Coursera, Product School, and FutureLearn were invisible to it.

**Principle: eliminate layers by falsification, cheapest first.** Reading one function and proving it *cannot* cause the symptom is faster than instrumenting the whole pipeline. Each elimination halves the search space. This is binary search applied to architecture.

---

## 6. Falsifying your own hypotheses

A stylistic audit was performed against a published taxonomy of machine-writing markers. Two categories were tested.

Lexical density — overused buzzwords and empty superlatives — showed a stark result:

```
Original CV:    0.23 flagged terms per 100 words
Generated CV:   3.96 flagged terms per 100 words   (17x)
```

Structural repetition — the "rule of three," a documented machine-writing tell — showed something else:

```
Original CV:    12.7 rule-of-three constructions per 1000 words
Generated CV:   12.2 per 1000 words
```

No difference. The hypothesis was wrong. Lists of three are simply normal professional English, and the taxonomy's inclusion of them does not make them diagnostic in this context.

This negative result was reported alongside the positive ones. That is not modesty; it is method. A diagnosis that reports only confirming evidence is not a diagnosis, it is advocacy — and a reader who later discovers the omitted negative has reason to doubt everything else in the report.

**Principle: test the hypotheses that could embarrass you, and publish the ones that fail.** The credibility of the findings you keep depends on the visible existence of findings you discarded.

---

## 7. Distinguishing constraints from parameters

The third symptom was that a role documented with fifteen distinct achievement bullets emerged as a single paragraph. The tempting explanations were prompt phrasing or model capability — both *parameters*, adjustable by tuning.

The actual cause was in the response schema:

```python
"properties": {
    "contentText": {"type": "string"},
    "evidenceIndexes": {"type": "array", "items": {"type": "integer"}},
}
```

A single string field. The model was not choosing to compress; it was structurally incapable of returning anything else. No prompt improvement and no model upgrade could have produced multiple bullets through that schema.

This distinction is load-bearing. A *parameter* is something you can tune to improve output within a fixed range of possible outputs. A *constraint* determines what the range of possible outputs is at all. Tuning a parameter when a constraint is binding produces effort with no result — and, worse, produces the false conclusion that the component is weak.

**Principle: before tuning, establish whether the desired output is representable at all.** If the schema, data model, or type signature cannot express the thing you want, no amount of instruction will produce it.

This is also why the eventual answer to "should we switch to a different language model?" was *not yet*. Changing a parameter while a constraint binds is uninterpretable: any observed difference is noise against a ceiling neither model can exceed.

---

## 8. Checking contracts between components

The prompt instructed the model to rewrite "work-experience bullet **points**." The schema provided one string. Two components, written at different times, each internally coherent, mutually contradictory.

This class of defect is invisible from inside either component. A code review of the prompt finds nothing wrong. A code review of the schema finds nothing wrong. The bug exists only in the relationship, and is therefore only findable by someone reading both with the specific question *"do these agree?"* in mind.

**Principle: bugs concentrate at interfaces, particularly between artefacts maintained by different mechanisms** — a prompt (prose, edited by hand) and a schema (structured, edited in code) drift apart precisely because nothing checks them against each other. When diagnosing, deliberately read adjacent components together rather than sequentially.

---

## 9. A method a junior developer can apply

Distilled into a repeatable sequence:

**1. Quantify the complaint.** Convert the subjective report into at least one number comparing input to output. Do this before forming any theory. The number determines where you look.

**2. Establish a control.** Find something the output should resemble. Same document before processing, a known-good prior run, a competitor's output. Without a control, you can describe the output but not judge it.

**3. Enumerate the layers.** Write down every component the data passes through. This is your search space and you cannot binary-search a space you have not listed.

**4. Read code, not comments.** For any behavioural claim, locate the implementing lines. If you cannot point at them, treat the claim as unverified.

**5. Eliminate cheaply first.** Prove a layer *cannot* cause the symptom rather than proving one does. Falsification is usually faster and always more conclusive.

**6. Reproduce in isolation.** Extract the suspect logic into a standalone script with real inputs. A hypothesis you have not executed is a guess.

**7. Separate constraints from parameters.** Ask whether the desired output is representable. If not, stop tuning and fix the constraint.

**8. Read interfaces in pairs.** Compare prompt against schema, schema against database, API response against client expectation.

**9. Test what could embarrass you, and report the failures.** Negative results are what make positive ones credible.

**10. Suspect the model last.** It is the component you control least and understand worst, which makes it a comfortable place to assign blame. Earn that conclusion by eliminating everything you actually wrote.

---

## 10. Conclusion

The investigation found four structural defects — a matching rule biased against specific skills, a parser blind to non-traditional credentials, a schema incapable of representing multiple bullets, and a parser that never extracted the candidate's name — plus a seventeen-fold increase in machine-writing markers traceable to a prompt containing extensive instructions on what not to fabricate and almost none on how to write.

None were model defects. All were in deterministic code, all were reproducible, and all were findable by reading carefully and running small experiments.

The broader lesson concerns where caution had been applied. The system's designers had built genuinely sophisticated safeguards against fabrication: schema-constrained output, mandatory evidence citation, database-level constraints, omission rather than substitution on verification failure. That discipline was real and worth preserving. But it had been implemented as *deletion* — dropping skills, dropping qualifications, compressing achievements — on the implicit assumption that removing content is the safe failure mode.

For a CV, it is not. A document that omits a candidate's degree, their tooling, and their name is not a cautious document. It is a wrong one, and it fails the person it was built to serve. Safety properties are only meaningful relative to a purpose, and a system that achieves its safety property by defeating its purpose has not been made safe — it has been made useless. Recognising that distinction is, ultimately, an engineering judgement rather than a technical one, and it is the judgement this diagnosis turned on.
